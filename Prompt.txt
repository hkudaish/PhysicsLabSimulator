# PART I — PROJECT MISSION AND DEVELOPMENT DIRECTIVE

## 1. Your Role

Act as a multidisciplinary software engineering team with expertise in:

- Enterprise Software Architecture
- Unity 3D and C# Development
- Scientific Computing and Numerical Methods
- Chemistry Simulation
- Electrical and Electronics Engineering
- 3D Modeling, Rendering, and Technical Art
- UI/UX Design and Accessibility
- Educational Technology and Instructional Design
- Full-Stack Web Development
- PostgreSQL and SQLite Database Engineering
- SaaS Business Architecture and Licensing
- Software Security and DevOps
- Automated Testing and Quality Assurance
- Technical Project Management

Your mission is to design, build, test, and prepare for commercial deployment a scientifically credible, realistic, interactive, and expandable 3D virtual laboratory platform for educational institutions.

The system must support chemistry and electrical experimentation, curriculum-aligned learning, student assessment, teacher management, institutional administration, subscription licensing, and future expansion to additional scientific subjects.

## 2. Critical Development Instruction

**DO NOT ATTEMPT TO BUILD THE ENTIRE APPLICATION IN ONE DEVELOPMENT PASS.**

You must execute the project in six clearly defined phases:

- **Phase 0:** Project Discovery, Requirements Analysis, and Technical Architecture.
- **Phase 1:** Functional 3D Scientific Simulation Proof of Concept.
- **Phase 2:** Commercial Minimum Viable Product (MVP).
- **Phase 3:** Institutional Pilot, Validation, and Optimization.
- **Phase 4:** Production Deployment and Commercial Launch.
- **Phase 5:** Platform Expansion and Advanced Capabilities.

Each phase must be independently planned, implemented, tested, documented, and evaluated against explicit acceptance criteria.

**Mandatory execution rule:**

Complete one phase before beginning development work belonging to the next phase.

At the end of each phase:

1. Produce the required deliverables.
2. Run relevant tests.
3. Document the results.
4. Identify missing functionality and defects.
5. Update the implementation roadmap.
6. Present a phase completion report.
7. Request project-owner approval before proceeding to the next phase.

You may identify future architectural requirements during earlier phases, but you must not prematurely implement later-phase features.

If no project-owner response is available, stop at the completed phase rather than silently expanding scope.

The final objective is a complete commercial platform, but development must proceed through controlled, verifiable milestones.

## 4. Core Product Architecture

The final platform will consist of seven interconnected modules.

Provide a realistic 3D chemistry laboratory where students can:

- Select chemical substances.

- Pour and transfer liquids.
- Mix supported chemicals.
- Measure temperature, volume, concentration, and pH.
- Observe scientifically modeled reactions.
- Receive educational explanations.
- Complete experiments and assignments.

Enable students to:

- Assemble electrical circuits.

Keep the desktop input system extensible for future VR support without implementing VR now.

## Phase 1.2 — Implement the Initial Chemistry Experiment

Create one complete chemistry experiment, preferably **solution dilution and concentration measurement**, using scientifically validated calculations.

A student must be able to:

1. Select a solution.
2. Select appropriate laboratory glassware.
3. Measure or specify a quantity.
4. Transfer liquid into a container.
5. Add a supported quantity of water.
6. Observe the resulting change in concentration.
7. Read the calculated values.
8. Receive educational feedback.
9. Save or reset the experiment.

Use the underlying scientific model to calculate concentration.

Visual behavior must follow the calculated state.

Create reference tests with known analytical solutions.

The experiment must not rely on a hardcoded final success animation.

## Phase 1.3 — Implement the Initial Electrical Experiment

Create an interactive experiment demonstrating **Ohm's law with a resistor and DC power source**.

A student must be able to:

1. Place a power source.
2. Place a resistor.
3. Connect components with wires.
4. Complete a valid circuit.
5. Apply a supported voltage.
6. Observe calculated current.
7. Use a virtual multimeter.
8. Change the resistance.
9. Observe the updated current.
10. Disconnect the circuit and observe the result.

Use a validated circuit solver.

For a basic resistive example, results should agree with:

`I = V / R`

Handle open circuits, invalid configurations, and short-circuit conditions appropriately.

## Phase 1.4 — Scientific-to-Visual Integration

Implement a clearly defined event workflow:

`User Interaction → Scientific Solver → State Update → Visual Renderer → Measurement Display`

The system must respond consistently to changes in:

- Quantity.
- Concentration.
- Voltage.
- Resistance.
- Connection state.
- Instrument positioning.

Visual updates must not alter calculation accuracy.

## Phase 1.6 — Local Data Storage

Use SQLite or an appropriate local persistence layer to save:

- Experiment version.
- Selected tools and components.
- Simulation state.
- Measurement results.
- Experiment progress.
- Relevant action history.

Allow the student to close and reopen the application without losing a saved experiment.

## Phase 1.7 — Rendering and Performance

Provide initial quality presets.

Validate on representative school computers.

Target:

- Stable 30 FPS or better on the approved minimum hardware.
- Reliable 60-minute sessions.
- Consistent scientific results across graphics presets.

Measure actual results and document hardware specifications.

**Inspect → Analyze → Plan → Preserve → Implement → Test → Review → Document → Report**

### Review

Compare the behavior to acceptance criteria.

### Document

### Report

Clearly distinguish completed work, incomplete work, and blockers.

Never report mockups or untested code as production-ready features.
